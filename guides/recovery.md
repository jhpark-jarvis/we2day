# 장애 복구

정상 서비스는 기존 Supabase 프로젝트를 유지합니다. 이 문서는 장애가 났을 때 확인할 범위와 복구 순서를 설명합니다. 명령을 그대로 운영 DB에 적용하는 자동 복원 스크립트가 아닙니다.

## 장애 범위부터 확인

| 상황 | 먼저 확인할 것 | 복구 범위 |
| --- | --- | --- |
| 앱만 접속되지 않음 | 웹/API 상태, HTTPS 인증서, DNS, 최근 배포 | 앱 이미지·설정·프록시 복귀. DB 복원 불필요 |
| VM 접속 불가·디스크 유실 | Supabase 콘솔과 Auth/Storage 가용성 | 새 서버에 앱·HTTPS·예약 재구축, 기존 Supabase 연결 |
| 일부 자료 오삭제·손상 | 대상·시각·다른 자료 영향, 남아 있는 휴지통 | 격리 사본에서 비교 후 복구 범위 결정 |
| Supabase 프로젝트 유실 | 접근 권한, 별도 DB·사진 사본과 복구키 | 별도 프로젝트·설정 준비 후 검토된 자료 복원 |

접속 오류만으로 DB를 이전 시점으로 되돌리지 마세요. 복구 대상·사본 생성 시각·중단할 작업·실행자·되돌릴 기준을 먼저 적습니다. 복구 중 일정 수정이나 업로드가 계속되면 사본과 운영 자료의 차이가 커질 수 있으므로 실제 복원 때 쓰기 중단 범위를 정해야 합니다.

## 서버 밖에 보관할 준비물

아래 항목의 **현재 서버 원본**, **별도 사본**, **다시 읽을 수 있는지**를 각각 확인합니다. 서버에 파일이 존재하거나 예약이 성공했다는 사실만으로 서버 유실 대비가 끝나지는 않습니다.

| 묶음 | 필요한 내용 | 보관 시 주의 |
| --- | --- | --- |
| 소스·실행 버전 | 공개 소스 revision, 웹/API/백업 이미지 버전·digest, Compose 구성 | 소스만 있으면 비밀 설정이 자동 복구되지는 않음 |
| 앱 설정 | 웹/API 환경 파일, 사이트 주소·허용 Origin, Maps·장소 검색 설정 | 비밀값은 공개 Git·일반 문서에 넣지 않음 |
| 예약 설정 | 알림 전용 DB 연결, VAPID 키·subject, 서비스·타이머 파일 | 기존 제한 역할과 기기별 동의 유지 |
| 백업 설정 | 수집 환경·DB 접속·Storage 서버 키·CA 파일, 검토 파일 | 관리자용 값은 앱 환경과 분리 |
| 암호화 자료 | DB와 사진 원본·미리보기가 포함된 검증 사본 | 같은 VM에만 두면 VM 유실 시 함께 사라짐 |
| 복구키 | 암호화 사본을 여는 별도 키 | 사본과 다른 위치·장치에도 보관하고 읽기 확인 |
| 외부 콘솔 | 클라우드·Supabase·DNS·Google·카카오·NAVER 계정 접근 및 복구 수단 | 계정 비밀번호·복구코드는 별도 보호 보관소 사용 |
| 인증·소셜 설정 | 활성 공급자, redirect 주소, 공급자 Client ID·Secret의 복원 또는 재발급 절차 | DB 사본에 콘솔 설정이 모두 들어 있다고 가정하지 않음 |
| HTTPS | 프록시 구성, 도메인 접근, 인증서 재발급·갱신 절차 | 기존 TLS 개인키를 복사한다면 별도 비밀자료로 보호 |

DB 백업은 Storage 객체 파일을 포함하지 않습니다. WE2DAY의 전체 수집은 DB와 객체 파일을 별도로 묶으므로 둘을 함께 복구해야 합니다. Supabase 공식 안내도 이 차이를 명시합니다. [Database Backups](https://supabase.com/docs/guides/platform/backups)

설정 사본을 만들 때는 암호화하고 접근 권한을 제한하세요. 암호화하기 전 평문과 셸 history·디버그 로그에 비밀값이 남지 않게 합니다. 암호화 DB·사진 묶음과 서버 설정 묶음은 내용과 복구 방법이 다르므로 서로 대체하지 않습니다. 현재 백업 수집기가 외부 콘솔 설정이나 전체 VM 설정까지 자동 수집하는 기능은 제공하지 않습니다.

## VM만 잃었을 때

1. 기존 Supabase 프로젝트가 정상인지 확인하고 프로젝트 삭제·DB 복원을 하지 않습니다.
2. 같은 아키텍처의 서버와 Docker를 준비하고, 검토된 소스 revision과 이미지 버전을 사용합니다. 새 서버의 포트와 기존 서비스 충돌도 확인합니다.
3. 보호된 별도 설정 사본에서 Compose와 환경 파일을 복원합니다. `.env.example`은 변수 안내이며 실제 설정의 대체물이 아닙니다. 알림·백업 예약은 아직 켜지 않습니다.
4. `docker compose config --quiet`로 구성 형식을 검사합니다. [환경 검사](deployment.md)는 복원한 경로를 `--web-env`, `--api-env`, `--worker-env`로 지정하고 VM 구성은 `--production --vm-env`를 사용해 웹/API의 Supabase·주소 설정을 대조합니다. 통과는 실제 접속 성공과 별개입니다.
5. [VM 배포 절차](deployment.md)에 따라 앱을 먼저 내부 주소로 실행합니다. 웹은 프록시 뒤에 두고 API·DB를 새로 인터넷에 노출하지 않습니다.
6. 두 계정 로그인·서로의 일정 조회·사진 열기·개인 일정 수정 권한을 확인합니다. 불필요한 실제 자료 생성 대신 기존 자료 조회와 별도 합성 검증을 사용합니다.
7. 정상 확인 후 DNS를 새 서버로 바꾸고 HTTPS를 발급·검사합니다. Origin·OAuth redirect·Maps 허용 주소가 서비스 주소와 맞는지 확인합니다. 인증서 경고를 우회하지 않습니다.
8. 외부 접속과 실제 기기 동작을 확인한 뒤 이전 서버의 예약이 중지됐는지 점검합니다. 한 서버에서만 알림·백업 예약을 켜고 실제 실행 결과를 확인합니다.

DNS 전환 전에 실패하면 기존 서버와 설정을 유지합니다. DNS 전환 뒤 실패하면 앱/프록시·주소의 이전 상태로 복귀할 수 있지만, 이미 새 DB에 쓰기가 발생했다면 주소만 되돌리는 것으로 끝내지 말고 자료 차이를 먼저 확인합니다.

## DB·사진을 복구해야 할 때

1. 어떤 사고를 어느 시점까지 복구할지 정합니다. 마지막 성공 사본의 실제 생성 시각과 필요한 SQL·사진 파일이 포함됐는지 확인합니다. 일일 예약이 있다는 사실만으로 복구 가능한 최신 시각을 보장하지 않습니다.
2. 원본·기존 암호화 사본·복구키를 보존하고, 별도 보호 공간에서 무결성 검사와 복호화를 수행합니다. [백업 절차](deployment.md#backup-collection)를 참고하세요.
3. 운영과 분리한 대상에서 DB 구조·역할·소유권·행수·RLS·Auth·Storage 객체를 복원합니다. 시험 환경에 운영의 외부 발송이나 예약을 연결하지 않습니다.
4. Supabase 관리 역할·확장·Auth/Storage 스키마와 새 대상의 차이를 검토합니다. 일반 PostgreSQL 시험의 역할 매핑을 관리형 프로젝트에 그대로 적용하지 않습니다. 이미 초기화된 운영 프로젝트에 전체 SQL을 무작정 덮어쓰지 않습니다.
5. DB 역할의 로그인 자격과 소셜 설정을 별도로 준비합니다. 기존 세션 유지 가능 여부와 재로그인 필요성을 확인합니다. 역할 비밀번호 복원에 관한 공급자 안내를 함께 검토하세요. [Supabase CLI 백업·복원](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
6. 사용자 신원·커플 연결·공동/개인 권한과 사진 파일 해시를 대조합니다. 익명·외부 계정의 접근 거부, 사진 미리보기/내려받기, 에이전트의 개인 일정 접근 제외도 확인합니다.
7. 앱을 격리 대상에 연결해 최소 기능을 확인하고, 실패 시 원본 설정으로 돌아갈 순서를 준비합니다. 실제 전환은 대상과 중단 시간·사용자 확인을 정한 뒤 별도로 실행합니다.

이 저장소의 암호화 검사와 격리 복구 검증은 운영 Supabase 프로젝트에 대한 자동 복원·자동 전환을 제공하지 않습니다. 원래 인증·외부 공급자 설정까지 복원한 실제 결과와 데이터 복구 시험을 구분합니다.

## 백업 보관과 정리

기본 보관 목표는 최근 일별 7개와 주별 4개이며 같은 사본이 두 조건을 동시에 충족할 수 있습니다. 실행 도구의 `review_candidates`는 검토 수치이며 삭제 명령이나 승인이 아닙니다.

자동 생성본 정리안을 검토할 때는 다음을 확인합니다.

- 모든 검토 대상의 복호화·무결성 검사가 성공하고, 최근 성공 사본과 별도 키 사본을 읽을 수 있음
- 자동 생성본과 수동·배포 checkpoint를 분리하고, 수동 사본은 별도 검토 전 보존
- 보관할 파일과 후보 목록·해시·크기를 기록하고 원본/설정과 혼동하지 않음
- 실패·손상·잠금 중·대상이 바뀐 경우 정리를 중단하고 정상 사본을 보존
- 서버 밖 사본과 설정 복구 준비, 실제 삭제 범위와 활성화 결정을 확인

현재 구현은 보관 후보 계산까지 제공하며 백업 파일을 자동 삭제하지 않습니다. 사진 휴지통과 DB·사진 전체 백업의 보관 정책도 서로 다릅니다.

## 준비 완료를 판단하는 기준

| 확인 | 준비 완료의 근거 |
| --- | --- |
| 자료 | 필요한 시점의 DB·사진을 격리 복원하고 권한·해시 확인 |
| 설정 | 서버 유실 후에도 보호된 설정 사본과 외부 계정 복구 수단 사용 가능 |
| 키 | 암호화 사본과 분리한 키를 다시 읽고 복호화 가능 |
| 재구축 | 버전·HTTPS·로그인·사진·예약 재개 절차와 실패 시 복귀 확인 |
| 최종 검토 | 검증된 범위·미확인 항목·실행자를 구분한 운영자 확인 |

문서 작성이나 파일 존재 확인만으로 모든 항목을 완료 처리하지 않습니다. 평소에는 정상 Supabase를 그대로 유지하고, 실제 장애가 발생하면 대상에 맞는 절차만 선택합니다.
